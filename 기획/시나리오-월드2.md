# 월드 2 상세 시나리오 — 별꽃광장

[전체 시나리오](시나리오.md) · [수정 방향](시나리오-수정방향.md) · [등장인물](등장인물.md)

## 목표와 개정 상태

2026-10-16: 기존 인트로와 2-1·2-2 본문을 보존하고, 2-3~2-5를 평가 기준 작성·평가·평가 검증 흐름으로 개정했습니다.

축제 가게 자리는 총 12개입니다. 9개는 이미 선정되었으며, 남은 3자리의 참가자를 선정하는 일을 사용자와 고디가 돕습니다. 이번에 검토할 신청서는 10개입니다. 이미 선정된 9개 가게와 이번 검토 대상 10개 신청서는 별도 집단입니다.

2-1은 업무 순서 배열 퍼즐 → 7개 요약 항목을 요구하는 프롬프트 작성의 두 활동으로 구성됩니다. 요약 활동은 실제 LLM 호출 없이 고디 보정 연출과 고정 md 요약 결과를 사용합니다. 신청서 전문·선정 기준·최종 결정 주체·의미상 동등 표현 판정 방식은 미정입니다. 요약 단계에서 참가자를 먼저 선정하지 않습니다.

2-2는 요약의 근거·원문 참조를 요청하는 검증자료 만들기입니다. 2-3에서 토리의 설명과 기존 선정 9곳을 참고해 평가 기준을 만들고, 2-4에서 신규 신청 10곳을 평가합니다. 2-5에서 평가 근거와 원문을 대조·검증한 뒤 결과를 토리에게 전달하며 월드를 마칩니다. 첫 시제품 범위는 월드 1입니다.

힌트·재도전 감점은 없고 상세 해설은 무료입니다. 현행 2-1·2-2는 LLM을 호출하지 않는 구성입니다. 2-3~2-5의 AI 실행 방식은 미정이며 실제 연결은 검증하지 않았습니다. 저장·보상·소요 시간은 미정입니다.

## 월드 인트로 — 서류를 안고 온 토리

고디와 나는 별꽃광장에 도착합니다. 토리가 서류뭉치를 한가득 들고 다가옵니다. 몇몇 서류는 토리의 품에서 벗어나 떨어지고 있습니다.

- 토리: “왕국지원단에서 오셨죠? 정말 다행이에요. 정말 나 혼자서는 어떻게 할 수가 없더라고요”
- 고디: “제가 좀 들어드릴게요”
- 토리: “감사합니다. 상황 보셔서 아시겠지만 이게 다 봄맞이축제에 참가하려는 분들이 제출한 서류예요. 축제기간동안 여기 별꽃광장에서 가게를 운영할 수 있거든요. 자리는 모두 12개인데, 9개는 이미 선정됐고 이제 3자리가 남았어요.”
- 나: “축제기간 동안 장사를 할 수 있으면 경쟁이 치열하겠네요”
- 토리: “네 그래서 남은 3자리에 참가할 분들을 고르는 일을 도와주셨으면 해요.”
- 고디&나: “네 알겠습니다!”

자리 수를 설명하는 두 대사는 기존 사용자 대사에 최신 수치를 연결한 수정안입니다. 서류가 떨어지는 모습은 대화 연출이며 별도 줍기 미니게임은 추가하지 않습니다. 토리가 서류를 맡고 있다는 설정을 사용하고 나이·권한·직책은 별도 확정하지 않습니다.

## 2-1 — 자료 요약하기

**유형: 드래그 순서 배열형 퍼즐 + 자유 입력 프롬프트 작성형 / 고정 결과 시뮬레이션**

한 스테이지 안에서 먼저 업무 순서를 정하고, 이어서 요약 요청을 작성합니다. 두 활동을 모두 완료해야 2-1이 완료됩니다. 퍼즐 성공만으로 별도 스테이지 완료·보상을 처리하지 않습니다. 요약 요청 재시도 시 이미 완료한 퍼즐을 다시 풀도록 요구하지 않습니다.

### 활동 A — 업무 순서 정하기

#### 시작 대사

- 나: “검토해야 할 신청서는 전부 10개네. 어떻게 작업해야 할까?”
- 고디: “같이 생각해보자.”

#### 진행 형태

| 항목 | 방식 |
| --- | --- |
| 중심 활동 | 업무 단계 5개를 확인 가능한 순서로 배열 |
| 화면·조작 | 섞인 퍼즐 조각 5개, 순서 배치 칸 5개, 드래그·재배치·제출 |
| 순서 | 도입 대화 → 퍼즐 배열 → 제출 → 판정·해설 → 같은 스테이지의 활동 B |
| 제출 | 다섯 단계의 배열 |
| AI 사용 | 고정 순서 대조, LLM 호출 없음 |

#### 퍼즐 조각과 통과 순서

아래 다섯 조각을 섞어 제시합니다. 사용자가 드래그로 아래 순서대로 배치하고 제출하면 통과합니다.

1. 신청서 살펴보기
2. 신청서를 각각 요약하기
3. 요약한 내용을 하나의 자료로 정리하기
4. 선정기준 적용하여 후보가게 고르기
5. 축제에 참여할 가게 선정

이 사례의 계획 순서를 익히는 퍼즐입니다. 모든 업무에 하나의 고정 절차만 가능하다고 일반화하지 않습니다. 이미 선정된 9개 가게를 다시 심사하는 단계는 추가하지 않습니다.

#### 판정·해설과 전환

- 다섯 조각이 지정 순서와 일치하면 활동 A를 통과합니다. 빈칸이나 순서 오류가 있으면 설명을 보고 현재 배열에서 수정합니다.
- 정답이어도 각 단계의 의미를 해설합니다. 원문 이해 → 신청서별 핵심 정보 보존 → 같은 항목으로 비교 준비 → 기준에 따른 후보 검토 → 최종 선정 순으로 설명합니다.
- 추가 힌트 초안: “가게들을 비교하기 전에 각 신청서의 내용을 알아야 하지 않을까요?”
- 활동 A 완료 대사: 고디 “맞아. 문서를 AI에 다 올리고 뽑아달라고 하기보다 중간중간 확인할 수 있도록 업무를 나누는게 요령이야!”
- `다음 활동`으로 같은 2-1 안의 활동 B에 이동합니다.

### 활동 B — 요약 프롬프트 작성하기

**유형: 자유 입력 프롬프트 작성형 / 고정 결과 시뮬레이션**

#### 문제와 학습 목표

**문제: “각각의 자료를 md 파일로 요약해보세요”**

검토할 10개 신청서를 읽고, 이후 비교에 필요한 항목을 포함한 요약 요청을 작성합니다. 이 스테이지에서 판정하는 것은 **필요한 정보를 항목별로 요구하는 프롬프트를 작성할 수 있는지**입니다. 실제 LLM 활용 능력이나 요약 결과 검증 능력을 이 활동 하나로 평가했다고 표현하지 않습니다.

실제 LLM·내부 API는 호출하지 않습니다. 기준을 충족한 입력에 고디가 조금 손봐주는 연출로 개입하고, 사전에 준비한 표준 프롬프트를 실행하는 것으로 보여줍니다. 실행 결과는 미리 작성한 신청서별 Markdown 요약본입니다. 실제 자유 입력의 생성 결과인 것처럼 표시하지 않고, 학습용 고정 결과라는 안내를 제공합니다.

#### 화면과 진행

| 항목 | 방식 |
| --- | --- |
| 자료 | 표현·구성이 제각각인 신청서 10개, 목록에서 원문 열람 |
| 입력 | 요약 요청을 직접 쓰는 입력창과 제출 버튼 |
| 활동 | 원문 읽기 → 프롬프트 작성 → 기준 확인 → 부족하면 수정 → 고디 보정 연출 → 준비된 요약 결과 → 다음 단계 |
| 판정 | 아래 7개 항목 요구 확인; 자료별 처리·md 출력의 별도 필수 판정 여부와 의미 인식 방식은 미확정 |
| 결과 | 신청서와 대응하는 md 요약본 10개를 미리 준비 |
| AI 호출 | 없음. 입력 판정도 LLM API를 사용하지 않음 |

사용자 결정은 7개 요약 항목을 모두 요구하면 통과하는 방향입니다. 자료별 처리·md 출력까지 명시적 통과 조건으로 삼을지, 누락 시 고디가 보완할지는 추가 확정 대상입니다. 파일명·다운로드·저장 조작은 아직 미정입니다.

#### 필수 요약 항목과 동등 표현

| 항목 | 인정할 표현 후보 |
| --- | --- |
| 신청자 | 신청인, 지원자, 신청한 사람 |
| 가게명 | 상호, 점포 이름, 매장 이름 |
| 주요 상품 | 대표 상품, 판매 품목, 주력 메뉴 |
| 가격 | 판매가, 상품별 금액, 메뉴 가격 |
| 작년 참여여부 | 지난해 참가 여부, 전년도 축제 참여 이력 |
| 예상 인기 | 기대되는 호응, 예상 수요, 인기를 끌 가능성 |
| 트렌드 | 유행, 최근 소비 경향, 요즘 선호하는 흐름 |

위 동등 표현은 구현 후보이며 목록을 확정한 것은 아닙니다. 정확한 단어 일치만 강제하지 않고 같은 정보를 요청하면 인정합니다. 역할 부여·특정 문장 순서·정해진 문구·불필요한 길이는 요구하지 않습니다.

#### 입력 판정과 피드백

- 미흡한 입력 예: “각각 자료를 요약해줘”.
- 이 경우 고디: **“좀 더 생각해볼까...”**
- 입력은 유지하고 제출을 완료 처리하지 않습니다. 사용자가 수정해 다시 제출할 수 있으며 재도전 감점은 없습니다.
- 보충 도움말 초안: “나중에 가게들을 비교하려면 어떤 정보가 필요할까?” 필요하면 누락된 항목을 안내합니다.
- 7개 항목을 의미상 모두 요청하면 고디 보정 단계로 진행합니다. 항목 이름을 단순히 나열했는지보다 그 정보를 요약에 포함하도록 요구했는지 확인합니다.
- “가격은 제외해줘”, “트렌드는 쓰지 마”처럼 제외하는 지시를 포함 요청으로 인정하지 않습니다. 동의어·부정·상충 지시의 판정 방식과 범위는 구현·검증 전입니다. 자유로운 모든 문장의 의미를 규칙만으로 정확히 인식할 수 있다고 보장하지 않습니다.

#### 고디 보정과 준비된 결과

- 통과 대사: 고디 **“요약할 때 중요한 내용은 빠뜨리지 않도록 꼼꼼하게 요구했구나. 수고했어!”**
- 고디는 의미를 유지하며 표준 프롬프트로 정돈해주는 연출을 합니다. 사용자의 입력과 보정된 요청을 구분해 보여주는 방식은 화면 설계 후보입니다.
- 표준 프롬프트 초안: “10개 신청서를 각각 별도의 Markdown 문서로 요약해줘. 신청자, 가게명, 주요 상품, 가격, 작년 참여여부, 예상 인기, 트렌드 항목으로 나눠 정리해줘. 원문에 없는 내용은 미기재로 표시하고, 신청자의 예상이나 의견은 그 사실을 밝혀줘.”
- 위 문구는 제작용 초안이며 사용자가 그대로 입력해야 하는 정답 문장이 아닙니다. 고디가 빠진 필수 항목을 대신 채워서 불충분한 입력을 통과시키지는 않습니다.
- 사전에 준비한 신청서별 요약본을 보여주고 다음 단계로 이동합니다. 결과 검토·편집을 이 스테이지의 별도 필수 과제로 추가하지 않습니다.
- 아직 가게 3곳을 선정하지 않습니다. 활동 B까지 완료하면 2-1을 마치고, 다음 2-2에서는 요약의 근거·원문 참조 부분을 명시하는 검증자료를 요청합니다.

#### 신청서 10개와 요약본 제작 기준

사용자 요구: 자료는 중구난방처럼 보이지만, 요청할 7개 항목의 정보를 대부분 포함해야 합니다. 신청서 전문과 요약본은 다음 제작 작업으로 남깁니다.

- 편지·상품 소개·짧은 메모 등 표현과 정보 순서가 다른 자료를 구성하되, 읽을 수 있는 분량으로 만듭니다.
- 신청자·상호·판매 품목·가격·참여 이력·예상 호응·유행 관련 정보가 문장 곳곳에 자연스럽게 들어가도록 설계합니다. 항목명 일곱 개를 그대로 나열한 동일 양식만 사용하지 않습니다.
- 예상 인기와 트렌드는 신청자가 밝힌 기대·경험·관찰 등 근거를 담습니다. 미래의 인기를 확정 사실처럼 쓰거나 AI가 외부 유행을 찾아낸 것으로 연출하지 않습니다.
- 일부 정보가 없다면 요약에 ‘미기재’로 남깁니다. ‘참여 이력 없음’과 ‘참여 여부 미기재’는 구분합니다. 누락 항목의 배분은 후속 확정 대상입니다.
- 신청서와 요약본은 일대일로 대응하고 가격·품목·이력·의견의 출처가 일치해야 합니다. 서로 다른 가게의 정보가 섞이지 않도록 원문-항목 대응표로 검수하는 것을 제안합니다.
- 기존 선정 완료 9개 가게와 신규 검토 신청서 10개는 별도 집단입니다.

#### 남은 설계와 검증

신청서 전문 10개·고정 요약본 10개·표준 프롬프트 확정, 동등 표현 사전과 부정·상충 처리, 정상/미흡/동의어/제외 요청의 판정 검증, md 파일 표시·저장 방식이 남아 있습니다. 이번 변경은 문서 설계이며 실제 동작 검증은 수행하지 않았습니다.

## 2-2 — 검증자료 만들기

**유형: 자유 입력 프롬프트 작성형 / 고디 보완·고정 결과 시뮬레이션**

### 상황과 시작 대사

신청서별 요약이 끝나자 토리가 놀랍니다. 보람님께 보고할 참고자료로, 요약의 근거를 원문에서 찾을 수 있는 검증자료를 부탁합니다.

- 토리: “벌써 신청서를 요약을 끝냈다고요? 이번 신입들은 정말 훌륭하네요!”
- 토리: “한 가지 더 부탁해도 될까요? 보람님께 보고할 때 쓸 참고자료가 필요해요. 요약자료랑 원문자료를 비교한 검증자료도 만들어주실 수 있을까요?”
- 고디&나: “네! 열심히 해볼게요”

보람이 보고를 받는 인물로 등장합니다. 이 대사만으로 보람의 직책이나 최종 선정 권한을 확정하지 않습니다.

### 문제와 진행 형태

**문제: 신청서별 요약 내용의 근거와 원문 참조 부분을 알 수 있는 검증자료를 요청하세요.**

| 항목 | 방식 |
| --- | --- |
| 자료 | 10개 신청서 원문과 2-1의 신청서별 요약본 |
| 중심 활동 | 요약의 근거·원문 참조 부분을 명시하는 프롬프트 작성 |
| 화면·조작 | 원문·요약 열람, 요청 입력창, 제출, 고디 보완 대화 |
| 순서 | 토리의 부탁 → 프롬프트 입력 → 요구 충족 확인 → 고디 파일명 보완 → 최종 프롬프트 표시 → 마무리 |
| 실행 방식 | 2-1의 요약 활동과 같은 비LLM·고정 결과 방식으로 연결하는 설계안. 실제 API 호출 없음 |

### 사용자 요청과 고디 보완

사용자님이 제시한 통과 입력 예시:

> 각각의 신청서 요약자료에 대한 근거를 명시해주고, 신청서 원문의 어떤 부분을 참고한 것인지 알 수 있도록 검증자료를 만들어줘.

이렇게 입력하면 고디가 말합니다.

- 고디: “검증자료 파일명은 신청서O_요약_검증.md로 통일해달라고 하면 더 좋겠다”

고디는 입력에 파일명 규칙을 덧붙여 최종 프롬프트를 완성합니다. 파일명 지시를 사용자가 처음부터 입력해야 하는 통과 조건으로 추가하지 않습니다.

최종 프롬프트 초안:

> 각각의 신청서 요약자료에 대한 근거를 명시해주고, 신청서 원문의 어떤 부분을 참고한 것인지 알 수 있도록 검증자료를 만들어줘. 검증자료 파일명은 신청서O_요약_검증.md로 통일해줘.

위 문구는 사용자 요청에 고디의 제안을 연결한 초안입니다. 정확한 문장을 외워 입력하는 활동으로 만들지 않습니다. 파일명에서 O는 신청서 식별자를 넣을 자리라는 해석을 제안하며, 숫자 표기·자릿수·원문 및 요약본의 이름과 대응 규칙은 추후 확정합니다.

최종 프롬프트를 보여주며 2-2를 마무리합니다. 결과 파일의 표시·다운로드를 추가로 필수 수행하게 하는 결정은 아직 없습니다. 고정 검증자료를 준비해 보여주는 방식은 2-1의 요약 활동과 연결하는 제작 후보입니다.

### 판정·학습 범위 — 구체화 초안

- 신청서별 요약의 근거를 요구하고, 신청서 원문의 어느 부분을 참고했는지 추적할 수 있도록 요청하면 통과하는 방향입니다.
- ‘근거’, ‘출처 문장’, ‘원문 위치’, ‘참고한 대목’ 등 동등한 요구는 인정하는 안입니다. 표현 후보·부정과 상충 지시의 판정은 설계·검증 전입니다.
- “검증자료 만들어줘”만 입력한 경우의 안내 대사·구체적인 부족 판정은 미정입니다. 수정과 재도전에 감점은 없습니다.
- 목표는 근거를 추적할 수 있는 자료를 요청하는 능력입니다. 프롬프트를 입력했다고 모든 요약이 정확하다고 판정하거나 학습자가 직접 검증을 수행한 것으로 기록하지 않습니다.
- 제작할 검증자료에는 요약 항목·요약 내용·원문 인용·원문 위치를 대응시키는 구성을 제안합니다. 누락·추측·불일치는 검증 완료로 숨기지 않고 확인 필요로 남기는 방향입니다. 실제 검증자료와 검토 활동은 아직 작성·확정하지 않았습니다.

### 남은 사항

원문·요약·검증자료의 대응, 검증자료 10개의 제작 여부와 표시 방식, 파일명 식별자 규칙, 동등 표현 판정, 부족한 입력의 피드백, 새 2-3 연결이 남아 있습니다. 소스 구현·실제 호출·판정 동작 테스트는 수행하지 않았습니다.

## 2-3 — 남은 세 자리의 선정 기준 만들기

**유형: 자료 비교형 + 자유 입력 프롬프트 작성형 + 기준 편집형**

### 상황과 시작 대사

신청서별 요약과 검증자료를 준비한 뒤, 남은 3자리에 어떤 가게를 추천할지 판단할 기준을 만듭니다. 토리의 설명과 이미 선정된 9개 가게 명단을 함께 살펴봅니다.

- 토리: “이제 남은 세 자리에 어떤 가게가 들어오면 좋을지 생각해 봐야겠어요. 먼저 선정된 아홉 가게의 명단도 가져왔어요.”
- 나: “신청서를 비교하기 전에, 어떤 기준으로 평가할지부터 정해 보자.”
- 고디: “토리가 말한 내용과 이미 정해진 가게들을 같이 보면 도움이 되겠네!”

### 문제와 진행 형태

**문제: 토리의 설명과 기존 선정 가게 9곳의 명단을 참고해, 신청 가게 10곳을 평가할 기준을 만들어 보세요.**

| 항목 | 방식 초안 |
| --- | --- |
| 자료 | 토리의 설명, 기존 선정 가게 9곳의 명단, 2-1의 요약 MD 10개, 2-2의 검증자료 |
| 중심 활동 | 선정 목적 확인 → 자료 비교 → AI에 기준 작성 요청 → 기준 검토·수정 |
| 화면·조작 | 토리 대화 다시 보기, 명단·요약 열람, 요청 입력, 기준 초안 편집 |
| 제출 | 기준별 의미·판단 방법·사용 자료·정보 부족 시 처리 방법을 담은 평가 기준 MD |
| 다음 단계 | 완성한 기준을 확정하고 2-4의 공통 평가 기준으로 사용 |

이미 선정된 9개 가게는 남은 자리의 구성을 생각하기 위한 참고자료입니다. 이들을 다시 심사하거나 신규 신청 가게 10곳에 포함하지 않습니다. 명단에 없는 상품·가격·인기 등을 AI가 임의로 보충하지 않도록 합니다.

### 1단계 — 토리의 설명과 명단 살펴보기

사용자는 토리가 중요하게 생각하는 점을 메모하고, 기존 9개 가게와 새 신청 가게의 상품 구성을 비교합니다. 기존 인트로에는 구체적인 선정 방침이 없으므로 다음은 후반부에 추가할 **토리 대사 초안**입니다.

- 토리: “광장에 온 분들이 여러 가게를 구경할 수 있으면 좋겠어요. 이미 정해진 가게들과 어떤 점이 겹치고 다른지도 봐 주세요.”
- 토리: “가격이나 작년 참여 경험도 참고할 수 있겠죠. 하지만 작년에 참여했다는 이유만으로 먼저 뽑지는 않았으면 해요.”
- 토리: “인기가 많을 거라는 말은 신청하신 분들의 예상일 수도 있으니, 어떤 근거가 있는지도 함께 살펴봐 주세요.”

기존 선정 가게 9곳의 실제 이름과 상품 구성은 별도 자료 제작 시 작성합니다. 이 단계에서 명단이 이미 만들어져 있다고 기록하지 않습니다. 명단에는 적어도 가게명과 주요 상품을 담아, 품목 구성의 겹침과 차이를 비교할 수 있게 준비합니다.

### 2단계 — AI에 평가 기준 작성 요청하기

참고 요청 예시:

> 토리가 설명한 내용과 이미 선정된 9개 가게의 명단을 참고해서, 남은 3자리에 들어올 신청 가게를 평가할 기준을 만들어줘. 각 기준의 목적, 판단 방법, 필요한 자료를 Markdown으로 정리해줘. 모든 신청 가게에 같은 기준을 적용하고, 자료가 부족할 때는 어떻게 처리할지도 적어줘. 아직 가게를 선정하지는 마.

문장을 그대로 따라 쓰게 하지 않습니다. 토리의 요구와 명단을 반영하고, 뒤에서 실제 적용할 수 있는 판단 방법을 요청하는지가 핵심입니다.

### 3단계 — 기준 초안 검토·수정하기

| 기준 후보 | 판단 방법 초안 | 검토할 점 |
| --- | --- | --- |
| 기존 가게와의 상품 구성 | 기존 9곳과 신청 가게의 주요 상품을 대조하고 겹치는 점·보완하는 점을 기록 | 상품이 겹친다는 이유만으로 자동 탈락시키지 않고 차이도 확인 |
| 가격의 접근성 | 신청서에 적힌 상품별 가격과 판매 단위를 확인해 비교 | 종류·용량이 다른 상품의 숫자만 단순 비교하지 않음 |
| 예상 인기의 근거 | 신청자가 제시한 판매 경험·호응 사례 등과 단순 기대를 구분 | 예상 인기를 확정된 사실로 취급하지 않음 |
| 트렌드와 상품의 관련성 | 신청서에 적힌 유행 관련 설명과 실제 판매 상품의 연결을 확인 | 자료에 없는 외부 유행이나 시장 정보를 만들어 넣지 않음 |
| 참여 경험의 활용 | 작년 참여 여부와 신청서에 적힌 경험의 활용 내용을 함께 확인 | 신규 참가라는 이유로 불리하게 처리하지 않음; 미기재와 불참 구분 |

이 표는 제작용 기준 후보이며 고정 정답이 아닙니다. 사용자가 토리의 요구와 자료를 근거로 기준을 조정할 수 있습니다. ‘좋은 가게’, ‘인기 있는 가게’처럼 판단 방법이 없는 항목은 구체화하도록 안내합니다.

평가 방식은 기준별 **적합·보완 필요·확인 필요**와 이유를 기록하는 초안입니다. 정보가 없으면 낮은 평가를 임의로 주지 않고 확인 필요로 남깁니다. 종합 비교에서 무엇을 우선할지도 이 단계에서 정합니다. 점수제를 선택한다면 배점·가중치·동점 처리까지 평가 전에 정해야 하며, 구체적인 수치는 후속 확정 대상입니다.

### 완료 조건과 전환

- 토리의 요구와 기존 9곳의 구성을 기준에 반영합니다.
- 각 기준에 판단 방법과 사용 자료를 적고, 모든 신규 신청 가게에 같은 방법을 적용할 수 있게 합니다.
- 정보 부족·종합 비교·동등한 후보 처리 방법을 정리합니다. 기준과 우선순위는 결과를 본 뒤 특정 가게에 맞춰 바꾸지 않습니다.
- 평가 기준을 MD 문서로 남깁니다. 파일명 초안은 `가게_평가기준.md`이며 실제 저장·다운로드 방식은 별도 설계합니다.

- 고디: “이제 어떤 점을 보고 비교할지 분명해졌어. 이 기준으로 열 가게를 살펴보자!”

## 2-4 — 같은 기준으로 신청 가게 평가하기

**유형: 자유 입력 프롬프트 작성형 + 평가 결과 비교형**

### 상황과 시작 대사

- 나: “방금 만든 기준을 각각의 요약자료에 적용해 보자.”
- 고디: “가게마다 같은 기준을 써야 해. 평가 이유도 같이 남기도록 부탁하자.”

### 문제와 진행 형태

**문제: 2-3에서 만든 기준을 신청 가게별 요약 MD 파일에 적용해 평가하고, 결과를 확인하세요.**

평가 대상은 2-1에서 작성한 신청서별 요약 MD 10개입니다. 2-2에서 만드는 검증자료는 요약의 근거를 확인하는 참고자료이며 평가 대상 신청서를 대신하지 않습니다.

| 항목 | 방식 초안 |
| --- | --- |
| 자료 | 2-3 평가 기준 MD, 신청서별 요약 MD 10개, 요약 검증자료와 신청서 원문 |
| 중심 활동 | 자료와 기준 지정 → AI에 평가 요청 → 개별 결과 확인 → 종합 비교 |
| 화면·조작 | 첨부 자료 확인, 요청 입력, 가게별 평가 보기, 전체 비교표 보기 |
| 제출 | 가게별 평가 MD, 전체 비교표, 추천 후보 3곳과 추천 이유·확인 필요 사항 |
| 다음 단계 | 평가 결과를 확정 사실로 전달하기 전에 2-5에서 검증 |

### 1단계 — 기준을 적용해 평가 요청하기

참고 요청 예시:

> 가게 평가 기준 문서를 그대로 적용해서 신청 가게 10곳의 요약 MD를 각각 평가해줘. 기준별 판단과 이유, 참고한 요약 항목을 남겨줘. 자료가 없는 내용은 추측하지 말고 확인 필요로 표시해줘. 전체 비교표와 남은 세 자리에 추천할 후보 3곳, 추천 이유도 정리해줘. 비교가 어려운 후보나 추가 확인이 필요한 내용은 별도로 알려줘.

사용자는 실제로 적용할 기준 문서와 요약 10개가 첨부됐는지 확인합니다. 기준 문서 대신 ‘알아서 좋은 가게를 골라줘’라고 요청하면 2-3의 기준을 지정하도록 안내합니다.

### 2단계 — 가게별 결과와 전체 비교표 보기

가게별 평가에는 신청서 식별자·가게명·적용 기준·기준별 판단·판단 이유·참고 요약 항목·확인 필요 사항을 담습니다. 파일명 초안은 `신청서O_평가.md`입니다.

전체 비교표는 같은 기준을 열로 두고 신청 가게 10곳을 행으로 배치합니다. 개별 평가와 종합 추천을 오가며 볼 수 있게 구성합니다. 추천 후보 3곳에는 다른 후보보다 우선한 이유와 기존 9곳의 구성을 어떻게 보완하는지도 표시합니다.

- 나: “추천된 가게만 볼 게 아니라, 나머지 가게의 평가 이유도 확인해야겠네.”
- 고디: “맞아. 근거가 부족해서 비교하기 어려운 곳도 있는지 보자.”

평가 결과가 나왔다는 이유만으로 정확성이 확인된 것은 아닙니다. 추천은 검증 전 초안으로 표시합니다. 정보 부족이나 동등한 후보 때문에 세 곳을 구분할 수 없다면 억지로 순위를 만들지 않고, 잠정 후보와 추가 확인 사항을 함께 보여줍니다.

### 완료 조건과 전환

- 신규 신청 가게 10곳 전체에 2-3의 같은 기준을 적용합니다.
- 개별 평가와 전체 비교표를 확인하고, 추천 이유·보류 이유·정보 부족을 살펴봅니다.
- 결과가 기준과 근거를 갖추었는지 확인할 검증자료가 필요함을 연결합니다. 결과 파일을 열기만 한 것을 평가 검증 완료로 기록하지 않습니다.

- 나: “평가 결과도 신청서와 맞는지 확인하고 전달하자.”
- 고디: “좋아. 이번에는 평가 근거까지 따라가 볼 수 있는 검증자료를 만들어 보자!”

## 2-5 — 평가 근거를 대조하고 검증하기

**유형: 자유 입력 프롬프트 작성형 + 원문 대조형 + 평가 수정형**

### 문제와 진행 형태

**문제: 2-4의 평가 결과를 검증할 자료를 만들고, 평가 기준·요약·신청서 원문과 실제로 대조해 보세요.**

| 항목 | 방식 초안 |
| --- | --- |
| 자료 | 평가 기준 MD, 가게별 평가 MD, 전체 비교표, 요약 MD, 요약 검증자료, 신청서 원문, 기존 선정 9곳 명단 |
| 중심 활동 | 평가 검증자료 요청 → 근거 추적 → 기준 적용 확인 → 수정·재검증 → 결과 전달 |
| 화면·조작 | 요청 입력, 평가·기준·원문 나란히 보기, 근거 위치 열기, 판정과 이유 기록, 수정 결과 확인 |
| 제출 | 가게별 평가 검증 MD, 종합 검증 결과, 수정한 평가·비교표·추천안 |
| 완료 | 실제 대조 기록과 남은 확인 사항을 담아 토리에게 전달 |

### 1단계 — 평가 검증자료 만들기

참고 요청 예시:

> 각 신청 가게의 평가 결과를 검증할 자료를 만들어줘. 평가 기준과 판단, 평가 근거가 된 요약 내용, 신청서 원문 인용과 위치를 연결해줘. 같은 기준이 모든 가게에 적용됐는지, 자료에 없는 내용을 근거로 판단했는지, 전체 비교표와 추천 이유가 개별 평가와 맞는지도 확인할 수 있게 해줘. 불일치나 근거 부족은 숨기지 말고 표시해줘.

고디 파일명 보완 대사 초안: “이번 검증자료는 `신청서O_평가_검증.md`로 구분하면 요약 검증자료와 헷갈리지 않겠다.”

| 검증자료 항목 | 담을 내용 |
| --- | --- |
| 대상 | 신청서 식별자·가게명·평가 결과의 해당 항목 |
| 적용 기준 | 2-3 기준 문서의 기준명과 판단 방법 |
| 평가 내용 | 기준별 판단과 이유 |
| 요약 근거 | 요약 MD의 관련 항목과 내용 |
| 원문 근거 | 원문 인용과 문단 등 찾을 수 있는 위치 |
| 대조 결과 | 일치·불일치·근거 부족 및 그 이유 |
| 조치 | 유지·수정·추가 확인과 수정 후 재검증 결과 |

기존 9곳과의 상품 구성 비교에는 해당 명단의 근거도 연결합니다. 원문에 없는 인기·유행 정보를 만들어 근거 칸을 채우지 않습니다. 검증자료 역시 확인해야 할 산출물이며, 생성되었다고 검증 완료로 처리하지 않습니다.

### 2단계 — 학습자가 실제로 검증하기

사용자는 각 가게의 기준별 평가에서 검증자료의 근거 위치를 열어 직접 대조하고, 판단과 이유를 남깁니다. 10곳 모두를 같은 항목으로 확인하며 추천된 3곳만 검토하고 나머지를 건너뛰지 않습니다.

1. 평가에 적힌 상품·가격·참여 이력 등이 해당 가게의 원문과 맞는지 확인합니다.
2. 예상 인기·트렌드 관련 설명이 신청자의 의견인지, 원문이 뒷받침하는 내용인지 구분합니다.
3. 평가 이유가 2-3에서 정한 기준과 판단 방법을 따르는지 확인합니다.
4. 같은 조건의 가게에 서로 다른 기준을 적용하거나 미기재를 불리한 사실로 바꾸지 않았는지 비교합니다.
5. 개별 평가·전체 비교표·추천 이유가 서로 일치하는지 확인합니다. 점수제를 사용했다면 합계·가중치·순위 계산도 대조합니다.

단순한 ‘확인했음’ 체크 대신 대조한 항목과 원문 위치, 일치 여부와 이유를 기록합니다. 자료가 부족한 경우에는 ‘원문에 가격 미기재’처럼 부족한 내용을 명시하고 추가 확인으로 남길 수 있습니다.

### 3단계 — 잘못된 평가 수정하고 다시 확인하기

연습 사례 초안:

| 발견한 문제 | 필요한 조치 |
| --- | --- |
| 원문은 작년 참여 여부 미기재인데 평가에는 신규 참가로 기재 | 미기재로 바로잡고 참여 경험 관련 평가 재검토 |
| 신청자의 ‘인기가 있을 것 같다’를 높은 수요가 입증된 근거로 사용 | 예상과 확인된 사실을 구분하고 판단 이유 수정 |
| 상품별 단위가 다른 가격을 숫자만 비교 | 판매 단위를 확인하고 비교 가능 여부 재판단 |
| 기준별 판단을 수정했는데 전체 비교표·추천 이유는 이전 상태 | 관련 결과를 함께 갱신하고 종합 추천 재검토 |

위 사례는 별도 제작할 학습 예시입니다. 실제 결과에 없는 오류를 억지로 찾게 하지 않습니다. 오류가 없다면 원문과 기준에 맞는 이유를 기록하고 유지합니다.

- 나: “이 평가는 원문보다 확실하게 말하고 있어. 확인할 수 있는 내용까지만 고치자.”
- 고디: “평가를 고쳤으니 비교표와 추천 이유에도 영향이 있는지 다시 확인하자.”

AI에 수정을 요청하거나 평가 문서를 직접 고친 뒤, 바뀐 항목과 영향을 받는 종합 결과를 다시 검증합니다. 요약 자체의 오류를 발견했다면 관련 요약·검증자료의 정정 사항도 남기고 연결된 평가를 갱신합니다. 이는 후반부 학습 흐름이며 이번 시나리오 편집에서 기존 2-1·2-2 본문을 수정하는 것은 아닙니다.

### 완료 조건과 전달할 결과

- 10개 가게의 평가에 대해 기준·요약·원문을 대조한 기록이 있습니다.
- 발견한 불일치는 수정 후 재확인하고, 근거 부족은 필요한 추가 확인과 함께 표시합니다.
- 개별 평가와 전체 비교표·추천안이 일치합니다.
- 토리에게 추천 후보 3곳과 이유, 평가 기준, 평가·검증자료, 남은 확인 사항을 함께 전달합니다. 근거가 부족해 세 곳을 확정 추천할 수 없다면 잠정안임을 명시합니다.

모든 정보가 확인된 것처럼 꾸미는 것을 완료 조건으로 삼지 않습니다. 학습 활동 완료와 후보 선정의 확정은 구분합니다. 최종 선정 권한은 별도 확정 대상이며, 게임에서는 검토 결과를 토리에게 전달하는 데까지 진행합니다.

## 월드 2 마무리 — 토리에게 결과 전달하기

2-5의 대조·수정·재검증을 마친 뒤 `토리에게 결과 전달`로 이어집니다. 게임 속 전달 연출입니다.

- 나: “토리, 신청 가게들을 같은 기준으로 평가했어요. 추천 후보와 이유를 정리했고, 평가가 원문에 맞는지도 확인했어요.”
- 고디: “평가 기준과 검증자료도 함께 준비했어요. 더 확인해야 할 내용은 따로 표시해 두었고요.”
- 토리: “정말 큰 도움이 됐어요! 어떤 이유로 추천했는지, 무엇을 더 확인해야 하는지까지 한눈에 알 수 있네요.”
- 토리: “AI로 이렇게 꼼꼼하게 일할 수 있다니 놀라워요. 요약부터 평가하고 검증하는 것까지, 정말 잘 활용하시는군요!”
- 나: “일을 나누고, 기준을 정하고, 결과를 확인하면서 하니까 정리할 수 있었어요.”
- 토리: “이 자료를 바탕으로 남은 세 자리의 참가자를 검토할게요. 정말 고마워요!”

토리가 안도하며 자료를 받아 들고, 고디와 나는 다음 여정을 준비합니다. 월드 2 완료 화면에는 **평가 기준·가게별 평가·검증 기록·최종 추천안**을 다시 볼 수 있게 하는 구성을 제안합니다.

## 후반부 제작과 검증에 남은 사항

이번 개정은 2-3~2-5와 엔딩의 시나리오 작성입니다. 기존 2-1·2-2 본문은 보존했습니다. 특히 기존 2-2는 최종 프롬프트 표시로 마무리되므로, 사용자가 앞서 말씀하신 ‘요약 검증자료를 이용한 실제 검증’까지 연결하려면 별도 수정 지시가 필요합니다. 이번에 해당 활동을 이미 수행한 것으로 바꾸지는 않습니다.

- 제작할 자료: 신청서 원문·요약·요약 검증자료 각 10개, 기존 선정 가게 9곳 명단, 평가 기준 예시, 평가·평가 검증자료와 전체 비교표·추천안.
- 확정할 설계: 토리의 구체적인 선정 방침, 기준별 판단 방법과 종합 비교 규칙, 동등한 후보·정보 부족 처리, 파일 식별자·표시·저장 방식.
- 실행 방식: 기존 2-1·2-2는 비LLM 고정 결과 구성입니다. 후반부의 AI 요청을 고정 결과 시뮬레이션으로 구현할지 실제 LLM으로 연결할지는 미정입니다. 고정 결과를 사용할 경우 학습용 사전 작성 결과임을 표시합니다.
- 검증할 사항: 자유 입력 판정과 피드백, 근거 연결·수정·재검증 동작, 자동 확인과 의미 판단의 범위. 판정하기 어려운 결과는 추가 확인 필요로 남깁니다.
- 실제 자료 제작·API 연결·게임 구현·플레이 테스트·학습 효과 검증은 수행하지 않았습니다. 첫 시제품의 월드 1 구현 범위는 유지합니다.

# 월드 2 상세 시나리오 — 별꽃광장

[전체 시나리오](시나리오.md) · [수정 방향](시나리오-수정방향.md) · [등장인물](등장인물.md)

## 목표와 개정 상태

2026-10-14: 별꽃광장 인트로와 통합된 2-1·2-2를 개정했습니다.

축제 가게 자리는 총 12개입니다. 9개는 이미 선정되었으며, 남은 3자리의 참가자를 선정하는 일을 사용자와 고디가 돕습니다. 이번에 검토할 신청서는 10개입니다. 이미 선정된 9개 가게와 이번 검토 대상 10개 신청서는 별도 집단입니다.

2-1은 업무 순서 배열 퍼즐 → 7개 요약 항목을 요구하는 프롬프트 작성의 두 활동으로 구성됩니다. 요약 활동은 실제 LLM 호출 없이 고디 보정 연출과 고정 md 요약 결과를 사용합니다. 신청서 전문·선정 기준·최종 결정 주체·의미상 동등 표현 판정 방식은 미정입니다. 요약 단계에서 참가자를 먼저 선정하지 않습니다.

2-2는 요약의 근거·원문 참조를 요청하는 검증자료 만들기입니다. 새 2-3 이후는 미정이며, 기존 2-4·2-5는 옛 번호를 표시해 보존했습니다. 새 참가자 선정 이야기의 현행 후반부로 확정한 내용이 아니며 후속 재설계 대상입니다. 첫 시제품 범위는 월드 1입니다.

힌트·재도전 감점은 없고 상세 해설은 무료입니다. 현행 2-1·2-2는 LLM을 호출하지 않는 구성입니다. 보존된 후반부의 API 구상은 재설계 전이며 실제 연결은 검증하지 않았습니다. 저장·보상·소요 시간은 미정입니다.

## 월드 인트로 — 서류를 안고 온 토리

고디와 나는 별꽃광장에 도착합니다. 토리가 서류뭉치를 한가득 들고 다가옵니다. 몇몇 서류는 토리의 품에서 벗어나 떨어지고 있습니다.

- 토리: “왕국지원단에서 오셨죠? 정말 다행이에요. 정말 나 혼자서는 어떻게 할 수가 없더라고요”
- 고디: “제가 좀 들어드릴게요”
- 토리: “감사합니다. 상황 보셔서 아시겠지만 이게 다 봄맞이축제에 참가하려는 분들이 제출한 서류예요. 축제기간동안 여기 별꽃광장에서 가게를 운영할 수 있거든요. 자리는 모두 12개인데, 9개는 이미 선정됐고 이제 3자리가 남았어요.”
- 나: “축제기간 동안 장사를 할 수 있으면 경쟁이 치열하겠네요”
- 토리: “네 그래서 남은 3자리에 참가할 분들을 고르는 일을 도와주셨으면 해요.”
- 고디&나: “네 알겠습니다!”

자리 수를 설명하는 두 대사는 기존 사용자 대사에 최신 수치를 연결한 수정안입니다. 서류가 떨어지는 모습은 대화 연출이며 별도 줍기 미니게임은 추가하지 않습니다. 토리가 서류를 맡고 있다는 설정을 사용하고 나이·권한·직책은 별도 확정하지 않습니다.

## 2-1 — 자료 요약하기

**유형: 드래그 순서 배열형 퍼즐 + 자유 입력 프롬프트 작성형 / 고정 결과 시뮬레이션**

한 스테이지 안에서 먼저 업무 순서를 정하고, 이어서 요약 요청을 작성합니다. 두 활동을 모두 완료해야 2-1이 완료됩니다. 퍼즐 성공만으로 별도 스테이지 완료·보상을 처리하지 않습니다. 요약 요청 재시도 시 이미 완료한 퍼즐을 다시 풀도록 요구하지 않습니다.

### 활동 A — 업무 순서 정하기

#### 시작 대사

- 나: “검토해야 할 신청서는 전부 10개네. 어떻게 작업해야 할까?”
- 고디: “같이 생각해보자.”

#### 진행 형태

| 항목 | 방식 |
| --- | --- |
| 중심 활동 | 업무 단계 5개를 확인 가능한 순서로 배열 |
| 화면·조작 | 섞인 퍼즐 조각 5개, 순서 배치 칸 5개, 드래그·재배치·제출 |
| 순서 | 도입 대화 → 퍼즐 배열 → 제출 → 판정·해설 → 같은 스테이지의 활동 B |
| 제출 | 다섯 단계의 배열 |
| AI 사용 | 고정 순서 대조, LLM 호출 없음 |

#### 퍼즐 조각과 통과 순서

아래 다섯 조각을 섞어 제시합니다. 사용자가 드래그로 아래 순서대로 배치하고 제출하면 통과합니다.

1. 신청서 살펴보기
2. 신청서를 각각 요약하기
3. 요약한 내용을 하나의 자료로 정리하기
4. 선정기준 적용하여 후보가게 고르기
5. 축제에 참여할 가게 선정

이 사례의 계획 순서를 익히는 퍼즐입니다. 모든 업무에 하나의 고정 절차만 가능하다고 일반화하지 않습니다. 이미 선정된 9개 가게를 다시 심사하는 단계는 추가하지 않습니다.

#### 판정·해설과 전환

- 다섯 조각이 지정 순서와 일치하면 활동 A를 통과합니다. 빈칸이나 순서 오류가 있으면 설명을 보고 현재 배열에서 수정합니다.
- 정답이어도 각 단계의 의미를 해설합니다. 원문 이해 → 신청서별 핵심 정보 보존 → 같은 항목으로 비교 준비 → 기준에 따른 후보 검토 → 최종 선정 순으로 설명합니다.
- 추가 힌트 초안: “가게들을 비교하기 전에 각 신청서의 내용을 알아야 하지 않을까요?”
- 활동 A 완료 대사: 고디 “맞아. 문서를 AI에 다 올리고 뽑아달라고 하기보다 중간중간 확인할 수 있도록 업무를 나누는게 요령이야!”
- `다음 활동`으로 같은 2-1 안의 활동 B에 이동합니다.

### 활동 B — 요약 프롬프트 작성하기

**유형: 자유 입력 프롬프트 작성형 / 고정 결과 시뮬레이션**

#### 문제와 학습 목표

**문제: “각각의 자료를 md 파일로 요약해보세요”**

검토할 10개 신청서를 읽고, 이후 비교에 필요한 항목을 포함한 요약 요청을 작성합니다. 이 스테이지에서 판정하는 것은 **필요한 정보를 항목별로 요구하는 프롬프트를 작성할 수 있는지**입니다. 실제 LLM 활용 능력이나 요약 결과 검증 능력을 이 활동 하나로 평가했다고 표현하지 않습니다.

실제 LLM·내부 API는 호출하지 않습니다. 기준을 충족한 입력에 고디가 조금 손봐주는 연출로 개입하고, 사전에 준비한 표준 프롬프트를 실행하는 것으로 보여줍니다. 실행 결과는 미리 작성한 신청서별 Markdown 요약본입니다. 실제 자유 입력의 생성 결과인 것처럼 표시하지 않고, 학습용 고정 결과라는 안내를 제공합니다.

#### 화면과 진행

| 항목 | 방식 |
| --- | --- |
| 자료 | 표현·구성이 제각각인 신청서 10개, 목록에서 원문 열람 |
| 입력 | 요약 요청을 직접 쓰는 입력창과 제출 버튼 |
| 활동 | 원문 읽기 → 프롬프트 작성 → 기준 확인 → 부족하면 수정 → 고디 보정 연출 → 준비된 요약 결과 → 다음 단계 |
| 판정 | 아래 7개 항목 요구 확인; 자료별 처리·md 출력의 별도 필수 판정 여부와 의미 인식 방식은 미확정 |
| 결과 | 신청서와 대응하는 md 요약본 10개를 미리 준비 |
| AI 호출 | 없음. 입력 판정도 LLM API를 사용하지 않음 |

사용자 결정은 7개 요약 항목을 모두 요구하면 통과하는 방향입니다. 자료별 처리·md 출력까지 명시적 통과 조건으로 삼을지, 누락 시 고디가 보완할지는 추가 확정 대상입니다. 파일명·다운로드·저장 조작은 아직 미정입니다.

#### 필수 요약 항목과 동등 표현

| 항목 | 인정할 표현 후보 |
| --- | --- |
| 신청자 | 신청인, 지원자, 신청한 사람 |
| 가게명 | 상호, 점포 이름, 매장 이름 |
| 주요 상품 | 대표 상품, 판매 품목, 주력 메뉴 |
| 가격 | 판매가, 상품별 금액, 메뉴 가격 |
| 작년 참여여부 | 지난해 참가 여부, 전년도 축제 참여 이력 |
| 예상 인기 | 기대되는 호응, 예상 수요, 인기를 끌 가능성 |
| 트렌드 | 유행, 최근 소비 경향, 요즘 선호하는 흐름 |

위 동등 표현은 구현 후보이며 목록을 확정한 것은 아닙니다. 정확한 단어 일치만 강제하지 않고 같은 정보를 요청하면 인정합니다. 역할 부여·특정 문장 순서·정해진 문구·불필요한 길이는 요구하지 않습니다.

#### 입력 판정과 피드백

- 미흡한 입력 예: “각각 자료를 요약해줘”.
- 이 경우 고디: **“좀 더 생각해볼까...”**
- 입력은 유지하고 제출을 완료 처리하지 않습니다. 사용자가 수정해 다시 제출할 수 있으며 재도전 감점은 없습니다.
- 보충 도움말 초안: “나중에 가게들을 비교하려면 어떤 정보가 필요할까?” 필요하면 누락된 항목을 안내합니다.
- 7개 항목을 의미상 모두 요청하면 고디 보정 단계로 진행합니다. 항목 이름을 단순히 나열했는지보다 그 정보를 요약에 포함하도록 요구했는지 확인합니다.
- “가격은 제외해줘”, “트렌드는 쓰지 마”처럼 제외하는 지시를 포함 요청으로 인정하지 않습니다. 동의어·부정·상충 지시의 판정 방식과 범위는 구현·검증 전입니다. 자유로운 모든 문장의 의미를 규칙만으로 정확히 인식할 수 있다고 보장하지 않습니다.

#### 고디 보정과 준비된 결과

- 통과 대사: 고디 **“요약할 때 중요한 내용은 빠뜨리지 않도록 꼼꼼하게 요구했구나. 수고했어!”**
- 고디는 의미를 유지하며 표준 프롬프트로 정돈해주는 연출을 합니다. 사용자의 입력과 보정된 요청을 구분해 보여주는 방식은 화면 설계 후보입니다.
- 표준 프롬프트 초안: “10개 신청서를 각각 별도의 Markdown 문서로 요약해줘. 신청자, 가게명, 주요 상품, 가격, 작년 참여여부, 예상 인기, 트렌드 항목으로 나눠 정리해줘. 원문에 없는 내용은 미기재로 표시하고, 신청자의 예상이나 의견은 그 사실을 밝혀줘.”
- 위 문구는 제작용 초안이며 사용자가 그대로 입력해야 하는 정답 문장이 아닙니다. 고디가 빠진 필수 항목을 대신 채워서 불충분한 입력을 통과시키지는 않습니다.
- 사전에 준비한 신청서별 요약본을 보여주고 다음 단계로 이동합니다. 결과 검토·편집을 이 스테이지의 별도 필수 과제로 추가하지 않습니다.
- 아직 가게 3곳을 선정하지 않습니다. 활동 B까지 완료하면 2-1을 마치고, 다음 2-2에서는 요약의 근거·원문 참조 부분을 명시하는 검증자료를 요청합니다.

#### 신청서 10개와 요약본 제작 기준

사용자 요구: 자료는 중구난방처럼 보이지만, 요청할 7개 항목의 정보를 대부분 포함해야 합니다. 신청서 전문과 요약본은 다음 제작 작업으로 남깁니다.

- 편지·상품 소개·짧은 메모 등 표현과 정보 순서가 다른 자료를 구성하되, 읽을 수 있는 분량으로 만듭니다.
- 신청자·상호·판매 품목·가격·참여 이력·예상 호응·유행 관련 정보가 문장 곳곳에 자연스럽게 들어가도록 설계합니다. 항목명 일곱 개를 그대로 나열한 동일 양식만 사용하지 않습니다.
- 예상 인기와 트렌드는 신청자가 밝힌 기대·경험·관찰 등 근거를 담습니다. 미래의 인기를 확정 사실처럼 쓰거나 AI가 외부 유행을 찾아낸 것으로 연출하지 않습니다.
- 일부 정보가 없다면 요약에 ‘미기재’로 남깁니다. ‘참여 이력 없음’과 ‘참여 여부 미기재’는 구분합니다. 누락 항목의 배분은 후속 확정 대상입니다.
- 신청서와 요약본은 일대일로 대응하고 가격·품목·이력·의견의 출처가 일치해야 합니다. 서로 다른 가게의 정보가 섞이지 않도록 원문-항목 대응표로 검수하는 것을 제안합니다.
- 기존 선정 완료 9개 가게와 신규 검토 신청서 10개는 별도 집단입니다.

#### 남은 설계와 검증

신청서 전문 10개·고정 요약본 10개·표준 프롬프트 확정, 동등 표현 사전과 부정·상충 처리, 정상/미흡/동의어/제외 요청의 판정 검증, md 파일 표시·저장 방식이 남아 있습니다. 이번 변경은 문서 설계이며 실제 동작 검증은 수행하지 않았습니다.

## 2-2 — 검증자료 만들기

**유형: 자유 입력 프롬프트 작성형 / 고디 보완·고정 결과 시뮬레이션**

### 상황과 시작 대사

신청서별 요약이 끝나자 토리가 놀랍니다. 보람님께 보고할 참고자료로, 요약의 근거를 원문에서 찾을 수 있는 검증자료를 부탁합니다.

- 토리: “벌써 신청서를 요약을 끝냈다고요? 이번 신입들은 정말 훌륭하네요!”
- 토리: “한 가지 더 부탁해도 될까요? 보람님께 보고할 때 쓸 참고자료가 필요해요. 요약자료랑 원문자료를 비교한 검증자료도 만들어주실 수 있을까요?”
- 고디&나: “네! 열심히 해볼게요”

보람이 보고를 받는 인물로 등장합니다. 이 대사만으로 보람의 직책이나 최종 선정 권한을 확정하지 않습니다.

### 문제와 진행 형태

**문제: 신청서별 요약 내용의 근거와 원문 참조 부분을 알 수 있는 검증자료를 요청하세요.**

| 항목 | 방식 |
| --- | --- |
| 자료 | 10개 신청서 원문과 2-1의 신청서별 요약본 |
| 중심 활동 | 요약의 근거·원문 참조 부분을 명시하는 프롬프트 작성 |
| 화면·조작 | 원문·요약 열람, 요청 입력창, 제출, 고디 보완 대화 |
| 순서 | 토리의 부탁 → 프롬프트 입력 → 요구 충족 확인 → 고디 파일명 보완 → 최종 프롬프트 표시 → 마무리 |
| 실행 방식 | 2-1의 요약 활동과 같은 비LLM·고정 결과 방식으로 연결하는 설계안. 실제 API 호출 없음 |

### 사용자 요청과 고디 보완

사용자님이 제시한 통과 입력 예시:

> 각각의 신청서 요약자료에 대한 근거를 명시해주고, 신청서 원문의 어떤 부분을 참고한 것인지 알 수 있도록 검증자료를 만들어줘.

이렇게 입력하면 고디가 말합니다.

- 고디: “검증자료 파일명은 신청서O_요약_검증.md로 통일해달라고 하면 더 좋겠다”

고디는 입력에 파일명 규칙을 덧붙여 최종 프롬프트를 완성합니다. 파일명 지시를 사용자가 처음부터 입력해야 하는 통과 조건으로 추가하지 않습니다.

최종 프롬프트 초안:

> 각각의 신청서 요약자료에 대한 근거를 명시해주고, 신청서 원문의 어떤 부분을 참고한 것인지 알 수 있도록 검증자료를 만들어줘. 검증자료 파일명은 신청서O_요약_검증.md로 통일해줘.

위 문구는 사용자 요청에 고디의 제안을 연결한 초안입니다. 정확한 문장을 외워 입력하는 활동으로 만들지 않습니다. 파일명에서 O는 신청서 식별자를 넣을 자리라는 해석을 제안하며, 숫자 표기·자릿수·원문 및 요약본의 이름과 대응 규칙은 추후 확정합니다.

최종 프롬프트를 보여주며 2-2를 마무리합니다. 결과 파일의 표시·다운로드를 추가로 필수 수행하게 하는 결정은 아직 없습니다. 고정 검증자료를 준비해 보여주는 방식은 2-1의 요약 활동과 연결하는 제작 후보입니다.

### 판정·학습 범위 — 구체화 초안

- 신청서별 요약의 근거를 요구하고, 신청서 원문의 어느 부분을 참고했는지 추적할 수 있도록 요청하면 통과하는 방향입니다.
- ‘근거’, ‘출처 문장’, ‘원문 위치’, ‘참고한 대목’ 등 동등한 요구는 인정하는 안입니다. 표현 후보·부정과 상충 지시의 판정은 설계·검증 전입니다.
- “검증자료 만들어줘”만 입력한 경우의 안내 대사·구체적인 부족 판정은 미정입니다. 수정과 재도전에 감점은 없습니다.
- 목표는 근거를 추적할 수 있는 자료를 요청하는 능력입니다. 프롬프트를 입력했다고 모든 요약이 정확하다고 판정하거나 학습자가 직접 검증을 수행한 것으로 기록하지 않습니다.
- 제작할 검증자료에는 요약 항목·요약 내용·원문 인용·원문 위치를 대응시키는 구성을 제안합니다. 누락·추측·불일치는 검증 완료로 숨기지 않고 확인 필요로 남기는 방향입니다. 실제 검증자료와 검토 활동은 아직 작성·확정하지 않았습니다.

### 남은 사항

원문·요약·검증자료의 대응, 검증자료 10개의 제작 여부와 표시 방식, 파일명 식별자 규칙, 동등 표현 판정, 부족한 입력의 피드백, 새 2-3 연결이 남아 있습니다. 소스 구현·실제 호출·판정 동작 테스트는 수행하지 않았습니다.

## 이전 2-4 — 결과가 어긋난 이유 찾기

**유형: 문서 편집형** / 보조: 직접 입력 대화형(LLM)·오류 표시형

### 진행 형태

| 항목 | 방식 초안 |
| --- | --- |
| 중심 활동 | 오류 진단·조치 이유·재요청/직접 편집 |
| 화면·조작 | 오류 예시·원문·문장 표시·편집·AI 대화 |
| 순서 | 문제 위치 표시 → 형식/근거 조치 정리 → 수정본 작성 → 장소 변경 적용 |
| 제출 | 오류 위치·수정 이유·요청·최종 공지 |
| AI 사용 | 첫 오류 초안은 고정 예시, 수정 대화는 실제 LLM 후보 |

**목표·사건**: 응답의 문제를 진단하고 요청 개선·근거 확인을 실제로 적용합니다.

- 율: “너무 길고 미정인 날짜를 확정한 연습 초안이 있어요.” 고드래곤: “고칠 형식과 확인할 사실을 나눠요.”
- 설명문: “모든 오류가 질문 탓은 아닙니다. 사실 확인을 재요청만으로 대신하지 않습니다.”
- 자료: 중앙 광장, 날짜 확인 중, 원하는 결과 두 문장. 예제는 원문에 없는 날짜를 표시합니다.

**수행**: 사전 작성 6문장·개최일 확정 오류 초안을 문장별로 표시하고 조치 이유를 남깁니다. AI 수정 요청 또는 직접 편집으로 날짜 미정인 두 문장 공지를 만듭니다. 실제 응답에 가짜 오류를 삽입하지 않습니다.

**산출물·검토**: 오류 위치·조치 이유·수정 요청·최종 공지. 다른 날짜로 추측하거나 형식만 바꿔서는 완료하지 않습니다.

**후속 부탁**: 장소가 동쪽 안내소로 변경됐다는 확정 자료를 제공해 최종 공지와 근거를 갱신합니다.

힌트 “형식과 사실은 다른 기준이에요.” 수정 “최신 자료를 근거로 바꿔주세요.” 완료: 율 “원인을 살펴보고 고쳤군요.”
## 이전 2-5 — 프롬프트 챔피언: 토리의 초대장 완성하기

**유형: 직접 입력 대화형(LLM)** / 보조: 질문 선택형 대화·자료 선택형·문서 편집형·근거 연결형

### 진행 형태

| 항목 | 방식 초안 |
| --- | --- |
| 중심 활동 | 정보 수집부터 최종 산출물까지 독립 수행 |
| 화면·조작 | 질문·메모·자료 서랍·AI 대화·편집·근거 연결·검토 결과 |
| 순서 | 질문 → 자료 선택 → 직접 요청 → 대조 → 재요청/편집 → 전달 → 도서관 후속 부탁 |
| 제출 | 초대장·사용 자료·근거·수정/유지 이유·새 안내문 |
| AI 사용 | 실제 내부망 LLM 활용 구상, 예시 모드와 기록 구분 |

### 재설계 상태와 목표

사용자님의 재설계 지시에 따라 작성한 대표 활동 초안입니다. 앞선 A~C 문제를 푸는 구조를 정보 수집 → 자료 선택 → AI 요청 → 검토 → 편집·재요청 → 최종 전달로 대체합니다. 2-1~2-4에서 연습한 방법을 독립적인 상황에 적용합니다.

목표는 적절한 문구를 고르는 것이 아니라 **필요한 정보를 확인하고 AI와 함께 실제로 쓸 수 있는 초대장을 완성하는 것**입니다. 완료 조건·자동 확인 기술·문항 난이도는 확정 전입니다.

### 사건과 도입 대사

- 토리: “친구들에게 장터 초대장을 보내고 싶어요. 짧고 알기 쉽게 써 주세요!”
- 율: “바로 작성하기 전에 무엇을 알아야 할지 살펴보세요.”
- 고드래곤: “토리에게 물어보고 자료를 확인할 수 있어요. 요청과 완성 문구는 직접 적어봐요.”
- 화면 목표: “확인한 정보로 친구들에게 전달할 초대장 만들기.”

주민과의 정보 수집 대화는 사전 작성된 질문·답변이고, 초안 작성 대화는 내부망 LLM API를 활용하는 후보입니다. 두 대화의 역할과 표시를 구분합니다.

### 1단계 — 필요한 정보 질문하기

처음에는 부탁만 보여주고 자료의 정답을 모두 미리 제공하지 않습니다. 질문 주제를 선택하면 토리의 답을 확인할 수 있습니다. 자유 질문 문장을 인식해 답하는 기능은 첫 설계에 포함하지 않는 안입니다.

| 질문 주제 버튼 | 토리의 대사 | 확인되는 조건 |
| --- | --- | --- |
| 누구에게 보내나요? | “마을 친구들에게 보내요. 처음 오는 친구도 있어요.” | 대상: 마을 친구들, 쉬운 표현 |
| 언제 어디서 열리나요? | “달맞이날 오전 10시에 중앙 광장에서 열려요.” | 날짜·시간·장소 |
| 비용은 있나요? | “참여는 무료예요.” | 참여 비용 |
| 얼마나 길게 쓸까요? | “두 문장이면 좋겠어요. 친구들에게 편하게 말해 주세요.” | 두 문장·친근한 말투 |
| 기념품도 있나요? | “아직 정하지 않았어요. 준다고 적지는 말아 주세요.” | 기념품 제공 약속 금지 |

질문은 순서와 횟수에 불이익을 주지 않습니다. 각 답은 확인 메모로 남고 다시 볼 수 있습니다. 핵심 정보를 모르더라도 AI 요청 화면은 열 수 있지만 최종 전달 전 부족한 조건을 확인해야 합니다. 질문 버튼 전부 클릭을 통과 기준으로 삼지 않습니다.

고드래곤 도움말: “누가 읽고, 어떤 정보가 꼭 필요한지 생각해 봐요.”

### 2단계 — 사용할 자료 고르기

자료 서랍에서 문서를 읽고 AI에게 첨부할 항목을 선택합니다. 자료는 게임의 가상 공개 내용으로 실제 개인정보를 다루지 않습니다.

| 자료 카드 | 내용 | 사용 판단 |
| --- | --- | --- |
| 이번 장터 확정 안내 | 달맞이날·오전10시·중앙 광장·무료. 이번 행사 최종본 표시 | 사실 작성의 기준 자료 |
| 지난 장터 안내 | 지난 행사·오후2시·서쪽 광장·무료. 지난 행사 표시 | 이번 행사의 사실 근거로 사용하지 않음 |
| 공지 문체 예시 | 친구에게 짧고 친근하게 초대하는 표현. 행사 사실 없음 | 문체 참고로 선택해도 되고 선택하지 않아도 됨 |
| 기념품 검토 메모 | 기념품 여부 미정. 확정 안내 아님 | 미정 상태를 이해할 자료, 제공 약속의 근거로 사용 불가 |

자료 선택은 수량을 맞히는 퀴즈가 아닙니다. 옛 자료를 문체 참고로 사용하려면 요청에서 용도를 구분할 수 있습니다. 최종 판단은 이번 행사 사실을 보존하고 과거 정보와 미확정 약속을 섞지 않았는지 중심으로 합니다.

자료 사용 설명 예시: “이번 확정 안내는 사실 자료, 공지 문체 예시는 표현 참고로 사용했습니다.” 고정 문구 복사를 요구하지 않습니다.

### 3단계 — AI에 직접 요청하기

왼쪽에는 부탁·확인 메모·자료 서랍, 오른쪽에는 대화 기록과 입력창을 둡니다. 사용자가 선택한 자료와 직접 쓴 요청을 전송하는 구조입니다. 첨부 자료가 무엇인지 전송 전 확인할 수 있어야 합니다.

- 입력 안내: “대상·원하는 결과·사용할 자료와 조건을 직접 적어 주세요.”
- 주 버튼: `보내기`.
- 보조 버튼: `자료 보기`, `요청 도움말`.
- 도움말은 짧은 질문을 제공하고 완성 프롬프트를 자동으로 정답처럼 채우지 않습니다.

참고 요청 예시: “이번 확정 안내만 사실 근거로 사용해서 마을 친구들에게 보낼 초대장을 두 문장으로 써 주세요. 친근하고 쉬운 말투로 쓰고, 미정인 기념품은 약속하지 마세요.”

역할 설정이나 위 문구와의 일치를 필수로 요구하지 않습니다. 내부망 API의 명세·인증·자료 전달 형식은 구현 전에 확인해야 합니다. 실제 응답은 달라질 수 있습니다.

### 4단계 — 결과를 근거와 대조하기

응답을 받은 후 `초안으로 가져오기`로 편집 영역에 복사합니다. AI 원응답과 사용자의 편집본을 구분하고 원응답을 몰래 변경하지 않습니다.

사용자는 편집본에서 관련 문장을 선택하고 확인 메모나 자료의 해당 항목을 연결합니다. 예: 시간 문장 ↔ 확정 안내의 오전10시. 메모·원본 항목을 클릭해 연결하는 UI 후보이며 정확한 조작은 추후 설계합니다.

검토 항목:

- 날짜·시간·장소가 이번 확정 안내와 맞는가?
- 참여 무료가 정확하게 전달되는가?
- 친구들이 이해할 두 문장인가?
- 기념품 등 미확정 약속이나 자료에 없는 사실이 추가됐는가?

‘검토했음’ 체크만으로 통과시키지 않습니다. 실제 최종 내용·근거 연결·누락과 충돌을 함께 확인하는 설계가 필요합니다.

**연습용 오류 사례**: “달맞이날 오후 2시에 서쪽 광장에서 장터가 열립니다. 무료로 참여하고 기념품도 받아 가세요!”

이 사례는 검토 예시로 별도 표시하며 실제 API가 반드시 이 답을 생성한다고 가정하지 않습니다. 최초 응답에 문제가 없다면 그대로 검토하고 완성할 수 있습니다.

고드래곤: “문장이 자연스러운 것과 자료에 맞는 것은 다를 수 있어요.”

### 5단계 — 재요청 또는 직접 편집하기

사용자는 부족한 부분을 AI에 다시 요청하거나 직접 수정합니다. 두 방법을 모두 허용하며 최소 대화 횟수·재요청 횟수를 요구하지 않습니다.

재요청 예시: “시간은 오전10시, 장소는 중앙 광장으로 고쳐 주세요. 기념품 약속은 빼고 무료 참여만 안내해 주세요.”

유효한 완성 문구 예시:

> 친구들아, 달맞이날 오전 10시에 중앙 광장에서 장터가 열려!
> 참여는 무료니까 함께 놀러 와.

다른 어순·동등한 시간 표현·다른 친근한 문장도 허용합니다. 첫 응답이 충분하면 불필요한 수정을 강제하지 않고 선택 이유를 남길 수 있습니다.

### 6단계 — 주민에게 최종안 전달하기

버튼: `완성본 검토하기`. 실제 외부 메시지를 보내지 않고 게임 내 토리에게 전달하는 연출입니다.

| 확인 항목 | 완료 조건 후보 | 확인 방식·한계 |
| --- | --- | --- |
| 핵심 사실 | 날짜·시간·장소·무료 정보 보존, 상충 표현 없음 | 필수 항목·근거 연결과 최종 문장 확인. 단어 포함만으로 정확하다고 판단하지 않음 |
| 미확정 내용 | 기념품 제공 등 근거 없는 약속 없음 | 사용자 표시·근거 대조, 의미 검토 방식 미정 |
| 형식 | 두 문장, 빈 문장이 아님 | 문장 경계 처리·동등 표현의 허용 규칙 설계 필요 |
| 대상 적합성 | 친구에게 이해하기 쉬운 문구 | 정해진 문체만 정답으로 취급하지 않음. 기준과 피드백 설계 필요 |
| 자료 활용 | 이번 사실 자료와 문체 참고를 구분 | 사용 이유·근거 관계 확인, 모든 카드 클릭 강제하지 않음 |

**검증 방식 미정**: 규칙으로 확인 가능한 항목은 자동 확인하고, 의미 판단에는 LLM 보조 피드백이나 별도 검토 방식을 검토합니다. LLM의 단일 점수로 합격을 결정하지 않습니다. 사용자 자기점검만으로 실제 활용 역량을 인증하지도 않습니다.

검토 시스템이 확실히 판단하지 못하면 `추가 확인 필요`로 표시하고 이유를 제시합니다. 최종 자동 판정이 아직 구현되지 않았다면 `연습 제출 완료`와 `검증 완료`를 구분합니다. 검토자를 새로 도입해야 한다고 확정한 것은 아닙니다.

### 수정 피드백과 완료 대사

- 누락 예시: 고드래곤 “처음 오는 친구가 어디로 가야 할지 알 수 있나요? 장소를 확인해 봐요.”
- 충돌 예시: 율 “원본은 오전10시인데 문구에는 오후2시가 있어요. 어느 쪽이 이번 자료인가요?”
- 미확정 약속 예시: 토리 “기념품은 아직 정하지 않았어요. 그 약속은 빼 주세요.”
- 완료: 토리 “친구들에게 전할 초대장이 완성됐어요. 고마워요!”
- 율: “요청하고, 확인하고, 고치는 과정까지 해냈군요.”

피드백은 실제로 발견한 문제에 맞춰 제시합니다. 오류가 없는 응답에 위 수정 대사를 강제로 출력하지 않습니다. 힌트·재요청·직접 편집 때문에 별점을 낮추지 않습니다.

### 예외와 기록 범위

- 빈 입력: 요청을 작성하도록 안내하며 전송하지 않습니다.
- 응답 대기: 진행 상태와 중복 전송 방지, 취소 방법을 설계합니다.
- API 오류: “응답을 받지 못했어요. 다시 시도하거나 연습 예시로 이어갈 수 있어요.” API 장애를 사용자 오답으로 처리하지 않습니다.
- 예시 모드: 사전 작성 응답임을 명확히 표시하고 실제 대화 활동과 완료 기록을 구분합니다.
- 중단: 메모·선택 자료·대화·편집본 중 어떤 상태를 저장할지 미정입니다.
- 기록 후보: 사용한 자료, 요청·후속 요청, 최초 초안·최종 편집본, 근거 연결, 피드백과 완료 상태. 수집·보존·로그 정책을 먼저 정하며 모두 저장하기로 확정하지 않습니다.

### 제작할 화면과 남은 결정

### 도움을 줄인 후속 부탁

토리가 장터 초대장 뒤에 도서관 체험 안내를 부탁합니다. 사용자가 자료 서랍에서 새 확정 운영표(별맞이날 오후3시·마을 도서관·무료·예약 불필요)를 찾아 대상·목적을 확인하고 두 문장의 안내를 완성합니다. 장터의 날짜·장소를 복사하지 않고 관련 근거를 갱신합니다. 안내 단서를 먼저 표시하지 않으며 필요할 때 힌트를 제공합니다. 결과·근거·수정 이유를 확인하는 같은 스테이지의 후속 활동이며 별도 시험은 아닙니다.

공통 대화 도입, 질문 주제·메모, 자료 서랍, 실제 AI 대화, 초안 편집·근거 연결, 검토 결과·완료 화면이 필요합니다. 같은 스테이지 안의 단계 전환으로 구성하며 자유 이동·별도 퀘스트 시스템은 추가하지 않습니다.

추가 결정: 자료·편집·근거 연결의 실제 조작, API 명세·응답 실패 대응, 최종 검증 규칙과 애매한 결과 처리, 도움말·저장·시간·보상. 실제 API 연결·소스코드·플레이 테스트는 수행하지 않았습니다.


## 월드 완료와 후속 검토

기존 구성은 2-1~2-4의 부분 연습을 2-5의 결과물로 연결했으나, 현행 2-1·2-2 통합·변경에 따라 새 2-3 이후의 참가자 선정 흐름을 다시 설계해야 합니다. 모든 스테이지의 산출물·근거·새 상황 적용은 검토 후보이며 자동 의미 판단·API 연동·시간·보상은 미정입니다. 실제 학습 효과를 확인한 상태가 아닙니다.

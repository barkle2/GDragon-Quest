# 월드 4 상세 시나리오 — 분주한 항구도시

[전체 시나리오](시나리오.md) · [등장인물](등장인물.md) · [수행형 활동과 검토](수행형활동과검토.md)

## 목표·이야기·공통 방식

2026-10-16: 사용자 제안에 따라 나와 고디가 항구 운영 담당 **해루**를 도와 축제 물품 기록을 정리하고, 급한 하역 작업을 찾아 경고하는 흐름으로 개정했습니다. 장소는 분주한 항구도시입니다. 해루는 기존 설정의 성인 수달 수인입니다.

문서마다 다른 정보를 LLM으로 구조화하고, 원문 검증을 거쳐 CSV·대시보드·업무 판단·반복 점검 스킬로 발전시킵니다. 다섯 스테이지는 같은 자료와 앞 단계 산출물을 이어 사용합니다.

| 스테이지 | 해결할 문제 | 산출물 |
| --- | --- | --- |
| 4-1 | 제각각인 문서에서 공통 관리 항목 찾기 | 항목 정의와 `하역물품목록.csv` 기본 틀 |
| 4-2 | 물품 기록을 같은 형식으로 정리하고 확인 | 데이터가 채워진 CSV·원문 대조 검증자료 |
| 4-3 | 많은 물품의 상황을 한눈에 살펴보기 | 항목별 슬라이서·막대그래프·선그래프·상세 목록 대시보드 |
| 4-4 | 지금 급하게 내려야 할 물품 찾기 | 긴급·임박·확인 필요 목록과 판단 근거 |
| 4-5 | 다음에도 같은 위험을 놓치지 않기 | 경고 스킬 명세·경고 메시지·시험 기록 |

이번 변경은 시나리오 작성입니다. 실제 데이터 파일·대시보드·스킬 프로그램을 제작하거나 하역 작업을 실행하지 않습니다. 첫 시제품의 월드 1 구현 범위는 유지하며, 힌트·수정·재도전에 감점은 없습니다.

## 도입 — 짐은 내렸는데 기록은 쌓이고

나와 고디가 항구에 도착합니다. 부두에는 축제 물품을 실은 배들이 드나들고, 해루의 작업대에는 편지·물품표·짧은 메모가 뒤섞여 있습니다.

- 고디&나: “안녕하세요 해루님. 항구도시에서도 일손이 부족하다고 들었습니다. 어떤 일을 도와드리면 될까요?”
- 해루: “아... 너희들이 해결사 듀오구나? 와줘서 정말 고마워!”
- 해루: “여기는 보다시피 항구도시라서 배들이 정말 많이 드나들거든. 특히 축제 때 사용할 물품들이 쉴새 없이 들어오고 있어.”
- 해루: “배들이 싣고 온 짐을 내리는 작업은 어찌어찌 하고 있는데, 하역한 물품 목록들을 정리할 시간이 없어서 곤란해. 너희들이 좀 도와줄 수 있을까?”
- 고디&나: “네 알겠습니다. 저희에게 맡겨주세요!”
- 나: “먼저 어떤 기록들이 있는지 살펴보자.”

### 이야기에서 사용할 자료

- 발송 안내문·수령 메모·물품표·하역 완료 기록 등 형식이 다른 가상 문서 묶음. 한 문서에 모든 항목이 있다고 가정하지 않습니다.
- 완료한 하역 기록과 아직 하역하지 못한 물품의 예정 기록. 완료시간이 없는 행도 포함해 이후 긴급 물품을 찾을 수 있게 합니다.
- 문서 식별자와 정정 이력. 원문과 CSV 행을 추적하고, 같은 물품의 발송·완료 문서를 중복 물품으로 세지 않도록 제작합니다.
- 해루의 하역 우선순위 메모와 장면의 기준 시각. 긴급 판단에 필요한 규칙은 4-4에서 명시합니다.

실제 원문 묶음과 수량·시간 등의 세부 값은 후속 제작 대상입니다. IDE의 다른 CSV나 실제 업무 자료를 이 이야기의 실습 데이터로 사용하지 않습니다.

## 4-1 — 서로 다른 기록의 공통점 찾기

**유형: 자료 탐색형 + 직접 입력 대화형(LLM) + 항목 설계형**

### 상황과 목표

나와 고디는 현재 하역물품 목록이 어떻게 관리되는지 살펴봅니다. 어떤 문서는 편지처럼, 어떤 문서는 표나 메모처럼 작성되어 같은 정보도 이름과 위치가 다릅니다.

- 나: “여기는 ‘보낸 사람’, 저기는 ‘발송인’이라고 적혀 있어. 물품을 비교하기가 어렵겠네.”
- 고디: “LLM의 도움을 받아 공통으로 관리할 항목부터 찾아보자.”

### 진행

원문 묶음을 읽고 LLM에 공통 항목과 각 항목의 의미를 정리하도록 요청합니다. 사용자는 제안이 원문에 있는 정보를 담는지, 업무에 필요한 내용을 빠뜨리지 않았는지 살펴봅니다.

> 축제 관련 하역 문서들을 같은 목록으로 관리하려고 해. 문서마다 표현이 다른 정보를 비교해서 공통으로 관리할 항목과 의미를 정리해줘. 항목을 제안한 근거도 원문에서 찾아줘. 아직 확인되지 않은 값은 추측하지 마.

| 공통 관리 항목 | 의미와 작성 원칙 |
| --- | --- |
| 발송인 | 물품을 보낸 사람·조직. 수령인과 구분 |
| 수령인 | 물품을 받을 사람·조직. 미정이면 확인 필요 |
| 물품명 | 실제 품목 이름. 비슷한 이름을 임의로 같은 물품으로 합치지 않음 |
| 수량 | 수치와 단위를 함께 보존. 예: 12상자, 8묶음 |
| 유의사항 | 취급 조건·연락 요청·하역 기한 등 원문의 조건 |
| 하역 예정시간 | 계획한 하역 시각. 실제 완료시각과 구분 |
| 하역 완료시간 | 실제 하역이 끝난 시각. 미완료·미기록 여부는 추가 확인 |

### 산출물·완료와 전환

일곱 항목의 정의를 정리하고 아래 헤더를 가진 `하역물품목록.csv` 기본 틀을 저장하는 활동으로 마칩니다. 4-1은 구조를 정하는 단계이며 전체 데이터를 채우고 검증하는 작업은 4-2에서 수행합니다.

```csv
발송인,수령인,물품명,수량,유의사항,하역 예정시간,하역 완료시간
```

- 나: “이제 같은 항목으로 정리할 수 있겠어.”
- 고디: “좋아. 다음에는 각 문서의 내용을 이 틀에 옮기고 원문과 확인해 보자.”

## 4-2 — CSV로 모으고 원문과 대조하기

**유형: 직접 입력 대화형(LLM) + 표 편집형 + 근거 연결형**

### 상황과 목표

- 해루: “정리하는 김에 수량이나 시간이 잘못 옮겨지지 않았는지도 확인해 주겠니?”
- 나: “검증자료를 만들어서 원문과 하나씩 맞춰 볼게요.”

4-1의 일곱 컬럼에 물품 데이터를 채우고, 각 값의 근거를 원문에서 확인합니다.

### 진행과 요청 예시

> 앞에서 정한 일곱 컬럼으로 하역물품목록.csv를 채워줘. 한 행이 어떤 하역 건의 물품인지 구분하고 수량의 단위를 보존해줘. 같은 건의 예정·완료 기록은 연결하되, 다른 물품을 임의로 합치지 마. 값이 없으면 빈칸으로 두고, 별도 검증자료에 행·항목별 원문 인용과 위치, 누락이나 충돌을 정리해줘.

일곱 업무 컬럼은 유지합니다. 행과 원문의 대응을 위한 식별 정보는 별도 검증자료에서 관리하는 설계안입니다. 같은 이름의 물품이라도 발송인·수령인·시간이 다르면 별도 하역 건일 수 있습니다. 문서 식별 정보만으로 연결이 불확실하면 합치지 않고 확인 필요로 남깁니다.

### 데이터와 검증자료 작성 원칙

- 시간은 날짜를 포함한 일관된 형식으로 정리하고 원문의 시간대·기준을 확인합니다. 날짜 없는 시간에 임의의 날짜를 붙이지 않습니다.
- 수량은 단위를 함께 기록합니다. 상자와 낱개를 변환하려면 원문에 포장당 수량 근거가 있어야 합니다.
- 완료시간 빈칸은 ‘미완료’ 확정값이 아닙니다. 검증자료에 해루가 확인한 미완료인지, 완료 여부가 미기록인지 구분합니다.
- 정정 문서는 이전 행을 무조건 추가하는 대신 해당 건인지 확인하고 정정 근거를 남깁니다. 서로 충돌하는 값은 임의 선택하지 않습니다.
- 쉼표·줄바꿈·따옴표가 들어간 유의사항을 CSV 규칙에 맞춰 처리하고 다시 열어 일곱 컬럼이 유지되는지 확인합니다.

검증자료 초안 이름은 `하역물품목록_검증.md`입니다. 원본 행의 식별 정보, 컬럼명, 옮긴 값, 원문 식별자·인용·위치, 대조 결과, 수정·확인 사항을 담습니다.

사용자는 LLM이 만든 검증자료의 인용도 원문에서 직접 확인합니다. 오류는 CSV와 검증자료를 함께 고친 뒤 다시 대조하고, 정보 부족은 별도 확인 목록으로 남깁니다. 검증자료 생성만으로 정확성을 확인한 것으로 처리하지 않습니다.

### 산출물·완료와 전환

- 데이터가 채워진 CSV, 행·항목별 검증자료, 미완료 확인·정보 부족 목록.
- 물품 누락·중복과 수량·단위·시간·유의사항을 확인하고 수정 기록을 남깁니다. 추적이 불가능한 행은 검증 완료로 표시하지 않습니다.
- 고디: “목록은 정리됐어. 이제 상황을 쉽게 살펴볼 수 있는 화면을 만들어 보자.”

## 4-3 — 한눈에 보는 하역 대시보드

**유형: 대시보드 구성 설계형 + 필터·그래프 확인형**

### 상황과 목표

- 해루: “표가 정리되니 좋구나. 그런데 수령인이나 물품별 상황을 바로 골라 볼 수도 있을까?”
- 나: “조건을 선택하면 그래프와 목록이 함께 바뀌도록 구성해 보자.”

각 항목의 슬라이서, 막대그래프·선그래프, 하단 상세 목록으로 대시보드를 설계하고 실습 화면에서 동작을 확인하는 흐름입니다. 구체적인 구현 도구는 후속 결정합니다.

### 대시보드 구성

| 영역 | 구성 초안 |
| --- | --- |
| 상단 | 자료 갱신 시각·현재 필터·전체 선택 해제 |
| 조건 선택 | 발송인·수령인·물품명·수량·유의사항·하역 예정시간·하역 완료시간 각각의 슬라이서 |
| 중앙 왼쪽 | 선택 조건의 물품별 또는 수령인별 하역 건수 막대그래프 |
| 중앙 오른쪽 | 날짜·시간대별 예정 건수와 완료 건수 선그래프 |
| 하단 | 선택 조건에 해당하는 일곱 컬럼의 상세 물품 목록·원문/검증자료 연결 |

수량 슬라이서는 단위를 구분해 선택하고, 시간 슬라이서는 날짜·시각 범위를 선택합니다. 유의사항은 원문 값을 고를 수 있게 하며, 내용 분류를 추가한다면 원문과 연결을 유지합니다. 빈값과 확인 필요 기록도 찾을 수 있도록 설계합니다.

> 검증한 하역물품목록으로 대시보드를 구성해줘. 일곱 항목마다 슬라이서를 두고, 선택 조건을 막대그래프·선그래프·하단 물품 목록에 함께 적용해줘. 막대그래프는 품목별 하역 건수, 선그래프는 시간대별 예정·완료 건수를 보여줘. 수량은 단위가 다른 값끼리 더하지 말고, 필터 조건과 집계 기준도 표시해줘.

기본 그래프는 건수로 집계해 단위 혼합을 피합니다. 물품 수량을 보여주는 추가 구성에서는 같은 물품·단위인지 확인합니다. 선그래프의 예정·완료는 각각 해당 시간 열을 기준으로 집계합니다. 여러 시간 슬라이서를 동시에 선택하면 모든 조건을 만족하는 행만 남는다는 점을 화면에 표시합니다.

### 확인 활동과 완료

수령인 선택 → 물품명 추가 선택 → 시간 범위 선택 → 전체 해제 순으로 실습하며 그래프의 건수와 하단 행 수를 직접 대조합니다. 결과가 없으면 ‘해당 조건의 기록 없음’으로 표시합니다. 미확인 시간을 임의로 특정 시간대나 0시로 집계하지 않습니다.

산출물은 대시보드 구성안·실습 화면과 필터 전후 확인 기록입니다. 화면 모양만 만드는 것을 데이터 연결 완료로 처리하지 않습니다.

- 해루: “필요한 물품을 바로 찾아볼 수 있겠네. 잠깐, 아직 내려야 할 물품 중에 급한 것도 있는 것 같아.”

## 4-4 — 지금 내려야 하는 물품 찾기

**유형: 조건 탐색형 + 원문 대조형 + 우선순위 보고형**

### 상황과 목표

대시보드에서 미완료 물품과 유의사항을 살펴보고 긴급 하역 대상과 이유를 해루에게 전달합니다. 예정시간이 이른 물품을 무조건 긴급하다고 판단하지 않습니다.

- 나: “이 물품은 아직 완료 기록이 없고, 유의사항에 하역 기한이 있어.”
- 고디: “실제로 미완료인지 확인하고, 지금 시각과 기한도 비교해 보자.”

### 해루의 판단 규칙 — 시나리오 초안

규칙은 판단 활동 전에 해루가 제공합니다. 아래 값과 사례는 제작용 가상 조건으로 실제 항구 운영 지침이 아닙니다.

| 상태 | 판별 규칙 |
| --- | --- |
| 긴급 | 미완료가 확인됐고 예정시간을 지났거나, 원문에 명시된 하역 기한에 도달·초과 |
| 임박 | 미완료가 확인됐고 명시된 하역 기한까지 30분 이내로 남음 |
| 확인 필요 | 완료 여부·시간·취급 조건이 불명확하거나 서로 충돌 |
| 완료·일반 | 완료가 확인됐거나 위 조건에 해당하지 않는 기록 |

‘상하기 쉬움’처럼 취급 주의만 있고 시간 기준이 없다면 임의의 기한을 만들지 않고 해루에게 확인합니다. 같은 행에 여러 조건이 겹치면 모두 이유로 남기고 긴급을 우선 표시합니다. 30분은 실습용 초안으로 운영 규칙 확정 시 조정할 수 있습니다.

### 탐색과 근거 확인

1. 장면의 기준 날짜·시각을 확인하고 선택 필터를 초기화해 전체 기록을 살펴봅니다.
2. 완료 여부 검증자료와 CSV의 완료시간을 함께 확인합니다. 빈칸만으로 미완료를 단정하지 않습니다.
3. 시간 슬라이서와 유의사항을 이용해 후보를 찾고 예정시간·명시 기한을 기준 시각과 비교합니다.
4. 후보의 수량·취급 조건·기한을 원문에서 다시 확인합니다.
5. 긴급·임박·확인 필요 목록에 대상과 근거, 해루에게 요청할 조치를 정리합니다.

연습 사례 초안: 기준 시각 10:00에 미완료가 확인된 물품 A의 예정시간이 09:40이면 긴급, 물품 B의 명시 하역 기한이 10:20이면 임박입니다. 물품 C의 완료시간이 빈칸이고 완료 여부도 모르면 확인 필요입니다. 같은 조건에서 이미 완료된 물품은 긴급 목록에 넣지 않습니다. 사례의 날짜와 원문은 자료 제작 때 함께 준비합니다.

### 산출물·완료와 전환

긴급·임박·확인 필요 목록, 원문과 시간 비교 근거, 조치 제안을 해루에게 전달합니다. 실제 하역 작업과 실행 순서는 해루가 확인합니다. 정보 부족을 급한 순위로 꾸미지 않습니다.

- 해루: “이 물품부터 확인해서 하역팀에 전달할게. 기록을 정리해 준 덕분에 놓칠 뻔한 일을 찾았구나!”
- 나: “다음에도 이런 상황이 생기면 미리 알려 주면 좋겠어요.”
- 고디: “방금 사용한 기준을 다시 쓸 수 있는 경고 스킬로 만들어 보자.”

## 4-5 — 다음에는 먼저 알려주는 경고 스킬

**유형: 재사용 스킬 작성형 + 조건·메시지 설계형 + 사례 시험형**

### 상황과 목표

4-4에서 사용한 판단 규칙을 반복해서 실행할 수 있는 **하역 경고 스킬**로 정리합니다. 여기서 스킬은 입력 자료·실행 절차·판단 규칙·출력 형식을 묶은 재사용 가능한 업무 지침입니다. 특정 제품의 스킬 설치나 상시 자동 실행을 뜻하지 않습니다.

- 해루: “매번 목록을 전부 읽지 않아도 급한 물품이 보이면 정말 좋겠어.”
- 고디: “새 목록을 넣으면 같은 기준으로 점검하고 이유까지 알려 주도록 만들자.”

### 스킬 설계와 요청 예시

> 검증된 CSV와 완료 여부 확인 자료, 기준 시각을 받아 긴급·임박·확인 필요 물품을 찾아주는 하역 경고 스킬을 설계해줘. 4-4의 규칙을 그대로 사용하고, 경고마다 대상·이유·근거 시각·다음 확인 행동을 보여줘. 완료한 물품은 긴급 경고에서 제외하고 정보 부족은 별도로 알려줘. 테스트 입력과 예상 결과도 만들어줘.

| 명세 항목 | 작성할 내용 |
| --- | --- |
| 이름·목적 | 하역 경고 스킬: 늦거나 기한이 가까운 물품을 놓치지 않도록 점검 |
| 입력 | 일곱 컬럼 CSV·원문 검증자료·완료 여부·명시 기한·판단 규칙·기준 시각 |
| 전처리 | 필수 컬럼·날짜 형식·중복·시간 충돌을 확인하고 판정 불가 기록 분리 |
| 절차 | 입력 확인 → 완료 여부 구분 → 예정시간·기한 비교 → 경고 분류 → 근거·메시지 출력 |
| 출력 | 긴급·임박·확인 필요 목록과 정상 처리 건수, 판단 기준 시각·자료 갱신 시각 |
| 실행 시점 | 우선 사용자가 새 목록을 넣고 실행하는 방식. 자동 감시 주기는 별도 구현 사항 |

경고 메시지 예시:

> [긴급] 물품 A: 하역 예정 09:40, 기준 시각 10:00, 미완료 확인. 예정시간이 20분 지났습니다. 수령인과 유의사항을 확인해 해루에게 전달하세요.

확인 필요 예시:

> [확인 필요] 물품 C: 완료시간과 완료 여부 확인 기록이 없습니다. 해루에게 상태를 확인한 뒤 긴급 여부를 다시 판단하세요.

### 사례로 시험하고 수정하기

| 시험 사례 | 기대 결과 |
| --- | --- |
| 미완료·예정시간 경과 | 긴급과 경과 이유 표시 |
| 미완료·명시 기한까지 30분 | 임박 표시; 30분 경계 포함 확인 |
| 미완료·명시 기한 도달 | 긴급 표시 |
| 완료 확인·예정시간 경과 | 긴급·임박 경고 제외 |
| 완료 여부 미기록 | 확인 필요; 미완료로 추정하지 않음 |
| 시간이 없거나 완료가 예정보다 빠름 | 누락·상충 사유를 확인하되 이른 완료만으로 오류 단정 금지 |
| 완료시각이 기준 시각보다 미래 | 시간 충돌 확인 필요 |
| 단위 다른 수량·동일 물품명 복수 건 | 합산하거나 한 건으로 뭉개지 않고 각각 처리 |
| 정상 기록·빈 목록·컬럼 누락 | 각각 경고 없음·대상 없음·입력 수정 안내로 구분 |

학습자는 예상 결과와 실제 실습 결과를 비교해 누락·오경고를 수정합니다. 완료 상태나 기한이 바뀐 새 입력으로 재실행해 이전 경고가 해소되는지도 확인합니다. 같은 자료를 반복 실행해 경고가 중복 누적되지 않도록 결과를 갱신하는 구성을 제안합니다.

### 산출물·완료 조건

- `하역경고_스킬.md` 명세 초안, 경고 메시지, 사례별 예상·실행 결과와 수정 기록.
- 4-4와 같은 규칙으로 긴급·임박·확인 필요를 구분하고 완료 건의 오경고를 막습니다.
- 규칙과 시간 계산은 확인 가능한 처리로 맡기고 LLM은 문서 해석·메시지 설명을 보조하는 설계입니다. 자유 문장의 기한 해석이 불확실하면 확인 필요로 남깁니다.
- 실제 실행 기능이 없으면 명세 작성·수동 사례 대조 완료로 표시합니다. 프로그램 시험이나 상시 경고 기능을 완성한 것으로 기록하지 않습니다.

## 월드 4 마무리 — 분주한 항구에 생긴 여유

나와 고디는 정리한 목록·검증자료·대시보드와 경고 스킬을 해루에게 보여줍니다.

- 나: “서로 다른 기록을 같은 항목으로 정리했어요. 원문과 확인한 자료도 함께 볼 수 있어요.”
- 고디: “조건을 골라 물품을 살펴보고, 급한 하역을 찾는 기준도 정리했어요. 새 목록으로 경고를 확인할 때 다시 사용할 수 있어요.”
- 해루: “물품이 어디에 적혀 있는지 찾느라 시간을 보내곤 했는데, 이제 상황을 한눈에 볼 수 있겠구나.”
- 해루: “급한 물품을 찾는 데다 다음에도 놓치지 않을 방법까지 생각해 주다니! 해결사 듀오라는 말이 괜히 나온 게 아니네. 정말 고마워!”
- 나: “고디, 목록 하나를 정리하는 일이 이렇게 여러 문제를 해결하는 데 이어지네.”
- 고디: “맞아. 자료를 같은 형식으로 정리하고 확인해야 다음 작업에도 믿고 쓸 수 있지.”

해루는 결과를 받아 다음 하역 점검을 준비합니다. 왕국지원단에서 나래 선배의 복귀 요청이 도착하고, 나와 고디는 처음 일을 시작했던 고디월드 왕국지원단으로 돌아갑니다. 스킬이 명세 단계라면 해루가 실제 자동 경고를 받고 있다고 연출하지 않습니다.

## 남은 제작·검증 사항

- 형식이 다른 원문 묶음, 완료 확인·정정 자료, CSV 예시·검증자료, 대시보드 예시와 긴급 판단 사례를 제작해야 합니다.
- 원문-하역 건 연결 규칙, 단위·날짜 처리, 명시 기한 해석, 경고 규칙·경계값·우선순위와 메시지를 확정해야 합니다.
- LLM 연결·파일 읽기/쓰기·대시보드 필터·집계·스킬 실행·저장 UI는 미구현입니다. 시뮬레이션과 실제 실행을 구분하며 API 장애는 사용자 오답으로 처리하지 않습니다.
- 이번에는 월드 4 상세안과 개발계획·진행상황만 수정합니다. 전체 시나리오·공통 교육표·게임 화면의 이전 활동 동기화는 후속 범위입니다.
- 실제 CSV 생성·데이터 검증·대시보드 제작·스킬 실행 시험·플레이 및 학습 효과 검증은 수행하지 않았습니다.
